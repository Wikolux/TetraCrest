# ADR-0005: Vision Framework

## Status

Accepted (implemented, M19 "Universal Vision Framework").

## Context

The platform needed a way to understand visual input — screenshots, PDFs, scanned documents, diagrams, charts, tables, receipts, forms, photos — usable by any current or future agent. This is the platform's second true capability framework (after Conversation), and the first one built after the pattern for "how a capability framework should be shaped" was already established.

## Problem

Two distinct risks needed to be avoided simultaneously: building Vision as `Agent → OpenAI` (or any vendor) directly, repeating the vendor-coupling mistake the whole AI Operating System exists to prevent; and building Vision as a fifth or sixth hand-copy of the registry/event/middleware infrastructure that Conversation, Runtime, Agent, Tool, and Executive/Research had each already written independently. A third, more specific risk: treating "vision" as one monolithic capability when in practice "describe a photo," "understand a scanned invoice," "extract a table," and "explain a flowchart" are different-enough tasks that forcing them into one interface would be awkward for any real provider to implement well.

## Alternatives Considered

1. **A `VisionAgent`** that directly calls a vendor's vision API. Rejected outright — this is the exact `Agent → OpenAI` shape the milestone's own brief explicitly ruled out, and would make Vision unreachable by any agent other than whichever one owned the integration.
2. **One monolithic `VisionProvider` with a single `analyze()` method** covering every use case. Rejected: image description, document understanding, text/table extraction, and diagram/chart analysis are different enough in their natural inputs/outputs that one interface would either be too vague to implement meaningfully or would accumulate provider-specific special cases.
3. **Four independent capability services** (image/document/extraction/analysis), each with its own provider ABC/registry/factory, unified only by a shared `VisionRuntime`/`VisionExecutor` and shared value objects. **Chosen.**
4. **Hand-copy a sixth registry/event/middleware implementation**, matching the existing (undesirable) precedent. Rejected in favor of extracting `GenericProviderRegistry`/`GenericEvent`/`GenericMiddleware` and building Vision as their first real consumer — see [ADR-0002](ADR-0002.md), which this decision directly motivated.
5. **A single image field on the request type** (`VisionRequest.image: bytes`). Rejected in favor of `inputs: tuple[VisionInput, ...]`, always plural, specifically so multi-image reasoning, document batches, and page-by-page processing are supported structurally from day one — "do not assume only one image" was an explicit design constraint, not an afterthought.

## Decision

Build `app/services/ai/vision/` mirroring the Conversation/Runtime relationship exactly: `Vision Agent (future) → Vision Framework → Vision Provider (abstract) → Provider implementation`. Four independent capability folders (`image/`, `document/`, `extraction/`, `analysis/`), each with its own `base_provider.py` (one capability ABC, one new abstract verb: `describe`/`understand`/`extract`/`analyze`), `registry.py`, `provider_factory.py`. A shared `BaseVisionProvider` holds only what's genuinely common (`health_check`/`provider_name`/`model_name` abstract; `initialize`/`shutdown`/`capabilities`/`metadata` concrete-with-safe-defaults) — deliberately no "analyze"-shaped method on the shared base, since each capability's primary verb differs.

`VisionRuntime`/`VisionExecutor` mirror `AIRuntime`/`RuntimeExecutor` exactly: provider resolution via factory, retry (with the same `AIProviderError`-is-not-retryable distinction), timeout and cancellation reused directly from `runtime/` (never re-implemented), middleware, hooks, and events. `VisionRequest`/`VisionResponse` compose `SharedExecutionContext`/`ExecutionMetrics` rather than redefining identity or metrics.

This milestone is also where `GenericProviderRegistry`, `GenericEvent`/`EventPublisher`, and `GenericMiddleware`/`GenericMiddlewarePipeline` were introduced (see [ADR-0002](ADR-0002.md)) — Vision was deliberately built as their first consumer, proving them out before the M19 completion pass back-applied them to five pre-existing subsystems.

## Consequences

**Positive**: Vision is fully exercised by 232 tests using only hand-written fakes — proving the framework provider-agnostic by construction rather than by convention. Zero vendor SDK/HTTP/OCR/image-library imports exist anywhere in the package, verified by grep as an explicit acceptance criterion. The four-capability split means a future provider can support, say, only image description without needing to implement document understanding, extraction, and analysis as well.

**Negative / accepted cost**: as of M19, **no concrete vision provider exists** — like the Tool Framework, this is architecture proven correct against fakes, not yet exercised against a real vendor's actual response shapes, rate limits, or error modes. The four-way capability split also means a single vendor that handles all four well (as most real multimodal vision APIs do) requires registering four separate provider classes (one per capability registry) rather than one — a reasonable API-design tradeoff for capability independence, but a real amount of registration boilerplate for a vendor that doesn't need the independence.

**A middleware bug caught during this work, relevant beyond Vision**: an early draft of `VisionMiddleware` overrode `GenericMiddleware.__call__` without re-applying `@abstractmethod`, which made `VisionMiddleware` silently instantiable (Python only treats a method as "still abstract" if no concrete override exists anywhere in the MRO — providing any override, even one that just raises `NotImplementedError`, counts as concrete). Caught by direct smoke-testing before the full test suite was written around it; documented as a standing rule in [Middleware.md](../02_KERNEL/Middleware.md) and [Coding_Standards.md](../06_DEVELOPMENT/Coding_Standards.md) so it isn't rediscovered by the next capability framework.
