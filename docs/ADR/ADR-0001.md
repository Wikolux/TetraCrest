# ADR-0001: Shared Execution Context

## Status

Accepted (implemented, M16.5 "Unified Execution Context" and M16.6 "Execution Identity Hardening").

## Context

By the time the Agent Framework (M16) was being built, three subsystems already existed, each with its own notion of "identity for the thing currently executing":

- The Kernel's `ExecutionContext`.
- The Runtime's `RuntimeContext`.
- The (about-to-exist) Agent Framework's own planned context type.

Each described the same underlying concept — which execution is this, what caused it, what session/organization/user does it belong to — from a slightly different angle, with different field names and no shared way to answer "which execution produced this artifact" across a boundary (e.g. an Agent calling into the Runtime).

## Problem

Without a single identity model:
- An Executive delegating to a Specialist, which calls a Tool, which calls the Runtime, has no way to prove those four executions belong to one causal chain — each subsystem's own context type has no field compatible with any other's.
- Every new subsystem (Tools, Vision) would face the same choice again: invent its own context type, or somehow reuse one of the three existing, incompatible ones.
- Correlating logs/events/responses across a multi-step delegation would require ad hoc, subsystem-specific glue code, rewritten for every new pair of subsystems that needed to talk to each other.

## Alternatives Considered

1. **Leave the three contexts independent, add manual translation at each boundary.** Rejected: this is an O(n²) problem as subsystems grow — every new pair needs its own translation, and nothing prevents drift between them.
2. **Pick one existing context type (e.g. `RuntimeContext`) and have everything else depend on it.** Rejected: `RuntimeContext` carries Runtime-specific fields (`provider`, `attempt`, `timeout`) that have no meaning for a Tool or an Agent; forcing every subsystem to depend on Runtime's own type would also violate the platform's dependency direction (Agents/Tools/Vision must not need to know about Runtime-specific concepts just to have an identity).
3. **A new, minimal, dependency-free shared type that every subsystem composes (holds as a field) rather than inherits from**, adding only what's genuinely specific to that layer on top. **Chosen.**

## Decision

Introduce `SharedExecutionContext` (`app/services/ai/shared/execution_context.py`) as the single execution identity every subsystem composes. It depends on nothing except `shared/execution_types.py` (a plain type alias leaf module), so every subsystem — Kernel, Runtime, Agents, Tools, Vision — can depend on it without risking a cycle.

Fields: `execution_id`, `parent_execution_id`, `correlation_id` (defaulting to `execution_id` when not given — a root execution starts its own correlation chain, matching distributed-tracing convention), `causation_id`, `session_id`, `request_id`, `organization_id`, `user_id`, `conversation_id`, `created_at`, `metadata`.

`RuntimeContext`, `AgentContext`, `ToolContext`, `VisionContext`, and the Kernel's own `ExecutionContext` each hold one as a `shared` field, with a hand-written `__init__` preserving backward-compatible flat-kwarg construction (e.g. `VisionContext(execution_id=...)` still works, building a `SharedExecutionContext` internally) and delegating properties (`context.execution_id` → `self.shared.execution_id`).

`.child(**overrides)` builds a nested execution's context: fresh `execution_id`/`request_id`, `parent_execution_id`/`causation_id` set to the parent's own `execution_id`, `correlation_id` propagated unchanged. `identity_fields()` returns the four fields (`execution_id`, `parent_execution_id`, `correlation_id`, `causation_id`) every execution artifact copies onto itself — the one place that mapping is defined, used by `RuntimeExecutor`, `AgentExecutor`, `ToolExecutor`, and `VisionExecutor` alike.

`RuntimeRequest.parent_shared` (added in M16.6, "Execution Identity Hardening") is what makes the whole mechanism actually usable in practice: a caller with its own context passes it as `parent_shared`, and the callee's executor builds its own context via `.child()` — this is what turns "Executive → Specialist → Tool → Runtime" into one real execution tree sharing a `correlation_id`, not just a type that theoretically supports it.

## Consequences

**Positive**: every execution in the platform, however deeply nested, is now reconstructable into a tree from its `correlation_id`/`parent_execution_id` alone. New subsystems (Vision, and future frameworks) get identity "for free" by composing `SharedExecutionContext`, with zero risk of inventing an incompatible parallel model.

**Negative / accepted cost**: `parent_shared` propagation is manual, not automatic — a caller that forgets to pass it silently starts a disconnected correlation chain rather than raising an error. This is a real, current sharp edge, documented explicitly in [Identity_Model.md](../02_KERNEL/Identity_Model.md).

**A hashability gap this decision surfaced**: `SharedExecutionContext` holds a `MappingProxyType` field (`metadata`), which a frozen dataclass's auto-generated `__hash__` cannot handle (it's unhashable). This was fixed with a custom `__hash__` based on `execution_id` alone. The same class of bug recurred independently for the Event System — see the "Consequences" note in [ADR-0002](ADR-0002.md) — and was eventually fixed with one shared strategy (`hash_event()`) rather than patched per type, which in retrospect should have been anticipated as a pattern the first time it was found here.
