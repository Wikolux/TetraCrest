# ADR-0002: Generic Registry, Event, and Middleware Infrastructure

## Status

Accepted (implemented: introduced during the M19 Vision milestone; back-applied to five pre-existing subsystems during the M19 completion pass).

## Context

By the time the Vision Framework (M19) was being built, five subsystems had each independently implemented the same three shapes:

- A **registry**: class-level `dict` + `threading.RLock`, `register`/`unregister`/`clear`/`get`/`is_registered`/`all_registered`, duplicate-registration rejected unless `overwrite=True`. Implemented separately by `ConversationProviderRegistry`, `AgentRegistry`, `ToolRegistry`, `SpecialistRegistry`.
- An **event + publisher**: a frozen dataclass with an `event_type` discriminator, `execution_id`, `timestamp`, `data`, plus a publisher storing subscribers and dispatching synchronously. Implemented separately by `RuntimeEvent`/`RuntimeEventPublisher`, `AgentEvent`/`AgentEventPublisher`, `ExecutiveEvent`/`ExecutiveEventPublisher`, `ToolEvent`/`ToolEventPublisher`, `ResearchEvent`/`ResearchEventPublisher`.
- A **middleware pipeline**: a `__call__(context, subject, call_next)` contract composed from the outside in, FastAPI/ASGI-style. Implemented separately by `RuntimeMiddleware`/`MiddlewarePipeline` and `ToolMiddleware`/`ToolMiddlewarePipeline`.

Vision needed all three again. Writing a sixth (registry), sixth (event/publisher), or third (middleware) hand-copy would have been the exact kind of duplication the platform's own design philosophy argues against.

## Problem

Continuing to hand-copy these shapes means: any bug fix or improvement (e.g. the eventual event-hashing fix) has to be applied N times and can silently drift between copies; a new engineer has to verify N nearly-identical implementations are actually equivalent rather than trusting one; and the platform's own stated principle ("compose, never duplicate") would be visibly violated by its own most recent milestone.

## Alternatives Considered

1. **Let Vision write its own fourth/sixth copy, matching the existing style.** Rejected: this was the status quo about to be perpetuated a sixth time; explicitly what the milestone's own instructions asked to avoid ("look for opportunities to unify... refactor toward shared abstractions rather than introducing parallel implementations").
2. **Extract shared generics, but only apply them to Vision — leave the five existing subsystems untouched indefinitely.** Considered as the safer initial step (and was, in fact, the approach taken for the Vision milestone itself, given the higher risk of touching five already-shipped subsystems' internals in the same change as building a new one). Ultimately judged incomplete — the duplication driving the decision would still exist for the five older subsystems.
3. **Extract shared generics for Vision, then migrate the five existing subsystems onto them in a dedicated, separate completion pass** with an explicit "preserve public APIs, preserve all behavior, preserve all tests" constraint. **Chosen**, executed in two steps (Vision first, then the M19 completion pass).

## Decision

Introduce three generics in `app/services/ai/shared/`:

- `GenericProviderRegistry[TKey, TValue]` (`provider_registry.py`) — `__init_subclass__` gives each concrete registry its own independent `_providers` dict and lock; `_registration_error: type[Exception]` is a class-level override point for the domain's own duplicate-registration exception.
- `GenericEvent`/`EventPublisher[TEvent]` (`events.py`) — `kw_only=True` fields so subclasses can add required fields after the base's defaulted ones; `correlation_id` defaults to `execution_id`, matching `SharedExecutionContext`'s own convention.
- `GenericMiddleware`/`GenericMiddlewarePipeline` (`middleware.py`) — the same onion-composition `run()` every existing middleware pipeline had already implemented independently.

Vision's own `VisionEvent`/`VisionEventPublisher`/`VisionMiddleware`/`VisionMiddlewarePipeline` and all four capability registries were built as genuine subclasses of these (verified via `isinstance`/`issubclass` in tests), not merely "shaped similarly."

During the M19 completion pass, the five pre-existing subsystems were migrated onto the same generics: `ConversationProviderRegistry`, `AgentRegistry`, `ToolRegistry`, `SpecialistRegistry` now extend `GenericProviderRegistry`; `RuntimeEvent`, `AgentEvent`, `ExecutiveEvent`, `ToolEvent`, `ResearchEvent` now subclass `GenericEvent`; `RuntimeMiddleware`/`MiddlewarePipeline` and `ToolMiddleware`/`ToolMiddlewarePipeline` now build on `GenericMiddleware`/`GenericMiddlewarePipeline`. Public method signatures, constructor shapes, and exception types were preserved exactly (`ToolRegistry`/`SpecialistRegistry` still wrap a `Registration` dataclass and expose their own extra methods, now implemented in terms of the generic base's `register`/`get`).

Two things were deliberately **not** migrated: `kernel.registry.RuntimeRegistry` (a genuinely different concept — instance-level, not class-level state) and `kernel.middleware.KernelMiddleware` (a genuinely different shape — `before_execute`/`after_execute`/`on_error`, not an onion `__call__`). Forcing either onto the new generics would have been a nominal renaming exercise, not a real deduplication.

## Consequences

**Positive**: three shapes now have exactly one implementation each, used by seven concrete subsystems (six event types, six registries counting Vision's four separately, three middleware pairs). Zero regressions across the full test suite (1987 → 2016 tests, all passing) confirm the migration changed no observable behavior.

**Negative / accepted cost**: `ToolRegistry`'s and `SpecialistRegistry`'s duplicate-registration error message changed from a domain-specific phrasing (`"Tool 'x' is already registered..."`) to the generic base's phrasing (`"'x' is already registered..."`) — verified safe only because every existing test asserted on the substring `"already registered"`, not the full message. A future test asserting an exact, domain-specific message would have caught this as a breaking change; none did.

**A related gap this surfaced**: migrating events onto `GenericEvent` required discovering (via direct smoke-testing) that a custom `__hash__` does not survive a subclass being re-decorated with `@dataclass` unless explicitly restated — this became the platform-wide event-hashing fix, documented in [Event_System.md](../02_KERNEL/Event_System.md).

**Deliberately out of scope**: `embedding.provider_factory`/`vector_store.store_factory` (outside `app/services/ai/`) have a structurally similar registry/factory shape but were not migrated — they belong to the Knowledge/Memory Engine (M12/M13), not the AI Operating System, and migrating them was judged out of scope for this pass. See [Dependency_Rules.md](../01_ARCHITECTURE/Dependency_Rules.md).
