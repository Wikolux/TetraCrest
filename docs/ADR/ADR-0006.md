# ADR-0006: Business Concepts and Memory Types

## Status

Accepted (discovered during CP-02 Milestone 2 — Professional Memory; codified here as a permanent, platform-wide precedent for every current and future Capability Pack).

## Context

CP-01 established a categorization convention for the Memory Framework: every durable fact a pack remembers is an ordinary `Memory` row, tagged with a pack-namespaced `memory_type` string (`personal_*` for CP-01), never a new table, schema, or storage mechanism ([CP-01 Architecture](../08_CAPABILITY_PACKS/CP-01_Personal_Intelligence_Pack/Architecture.md) §9; [ARCHITECTURE_FREEZE_v1.md](../ARCHITECTURE_FREEZE_v1.md)). CP-02 adopted the identical discipline under its own `product_*` namespace ([CP-02 Architecture](../08_CAPABILITY_PACKS/CP-02_Product_Management_Intelligence_Pack/Architecture.md) §5–§6), and CP-02's Architecture Readiness Review independently verified this reuse was sound ([ARR](../08_CAPABILITY_PACKS/CP-02_Product_Management_Intelligence_Pack/ARR.md) §11).

While implementing CP-02 Milestone 1 (Shared Domain Models), the CP-02 Architecture and Product Artifact Model (Architecture §7) named nine business entities: Product, Feature/Initiative, Roadmap Item, Metric, Discovery Finding, Research Finding, Stakeholder, Decision Record, and **Portfolio**. Eight of the nine map cleanly onto their own `memory_type`. Portfolio does not — Architecture §12 and the ARR's own Ownership Matrix (§4) had already, independently, assigned Portfolio the *same* owner as Roadmap State ("Portfolio Records ... same owner as Roadmaps — portfolio view is a grain extension, not a separate owner"), not a distinct memory category of its own.

Milestone 2 (Professional Memory) is where this stopped being a documented architectural intention and became a real implementation decision: the milestone's task explicitly required a `remember_portfolio()` method, and implementing it required deciding, concretely, whether to give Portfolio its own `product_portfolio` memory type or to honor the ownership decision Architecture §12 had already made.

## Problem

If every named business entity automatically received its own memory type, two things would follow, both undesirable:

1. **The memory-type namespace would grow in lockstep with the domain model**, regardless of whether a new category was actually needed for retrieval, ownership, or lifecycle purposes distinct from an existing one. Portfolio has no retrieval need, no lifecycle, and no ownership rule that Roadmap State doesn't already have — a `product_portfolio` type would exist purely because "Portfolio" is a noun in the Architecture document, not because the Memory Framework needed it to behave differently from `product_roadmap` in any way.
2. **A future Capability Pack would have no precedent to check against.** Without a stated rule, the next engineer facing the same situation (a real business concept with no genuinely distinct memory behavior) has no way to know whether inventing a new type is the established pattern or a one-off mistake CP-02 happened to make.

Both failure modes trace back to the same unexamined assumption: that a business concept and a memory type are the same kind of thing, and should therefore have a one-to-one relationship. This ADR exists to state, explicitly, that they are not.

## Alternatives Considered

1. **Give Portfolio its own `product_portfolio` memory type**, matching the naming pattern of the other eight entities purely for surface consistency. Rejected: this would be a new `memory_type` value introduced for taxonomic tidiness alone, not because anything about Portfolio's retrieval, ownership, retention, or lifecycle differs from `product_roadmap`. It would also directly contradict Architecture §12's and the ARR's own already-approved ownership decision, silently reversing an architectural conclusion inside an implementation milestone — exactly the "no silent redesigns" violation the [Version 1 Development Guide](../VERSION_1_DEVELOPMENT_GUIDE.md) §3 forbids.
2. **Give Portfolio no `remember_*` capability at all**, on the grounds that it has no memory type to write to. Rejected: the Implementation Plan and Milestone 2's own task explicitly required a `remember_portfolio()` method, and Portfolio-level understanding is real, useful information a PM will want the system to retain — declining to store it at all would be a functional regression relative to what the pack needs to do, not an architectural principle.
3. **Have `remember_portfolio()` write under the existing `product_roadmap` type, composing its own natural-language content directly** (since `Portfolio` itself deliberately has no `to_memory_content()` — a decision already made in Milestone 1, consistent with it having no `memory_type`). **Chosen.** This honors the ownership decision Architecture §12 and the ARR already made, requires no new taxonomy, and still gives the pack a genuine, working way to remember portfolio-level understanding.

## Decision

**A business concept named in an Architecture or Product Artifact Model does not automatically require its own memory type.** A new `memory_type` is warranted only when a concept has a genuine reason to be retrieved, owned, retained, or reasoned about differently from an already-approved category — never merely because it has its own name, its own entry in an entity-relationship table, or its own domain object in code.

Where a business concept's memory behavior is identical to an already-approved category's, that concept **reuses** the existing category. The relationship is expressed in code (a `remember_*()` method that writes under the existing `memory_type`) and in documentation (an explicit statement of which category owns the concept and why), never left implicit.

This decision does not modify `AgentMemory`, `MemoryAdapter`, `AIMemoryService`, or any frozen interface. It is a **categorization discipline** — the same kind of discipline CP-01's and CP-02's own `memory_type` namespacing conventions already are — not a change to platform mechanism.

## Examples

**Portfolio → `product_roadmap`, not `product_portfolio`.** A Portfolio is the PM's own set of Products considered together (Architecture §7); Architecture §12 already established that portfolio-level reasoning is "a grain extension of Strategy, not a parallel decision mechanism." `ProfessionalMemoryService.remember_portfolio()` (CP-02 Milestone 2) writes under `MEMORY_TYPE_ROADMAP`, composing its own content rather than calling a `to_memory_content()` the domain object deliberately does not have.

**A counter-example, for contrast — Decision Record → its own `product_decision` type.** Unlike Portfolio, a Decision Record has a genuinely distinct retrieval need (precedent-surfacing, Architecture §8), a genuinely distinct structural requirement (mandatory evidence and counterpoint fields, ARR §7), and genuinely distinct consumers (Strategy, Portfolio, Career Development) that read it specifically *as* a decision, not as a roadmap item or a feature. It earns its own category because its behavior differs, not because it has its own name.

## Future Guidance

Before a future Capability Pack (CP-03 onward) introduces a new `memory_type`, its Architecture phase (Phase 2) must answer, for the entity in question: does this concept need to be retrieved differently, owned differently, retained differently, or reasoned about differently than every category already approved for that pack? If the honest answer is no, the concept is documented as a rendering or grouping of an existing category — exactly as this ADR resolves Portfolio — not given a new type. This question belongs in Architecture Readiness Review (Phase 2.5) alongside the existing ownership and traceability checks: an ARR reviewing a new memory type should ask what distinct behavior justifies it, the same way CP-02's own ARR (§7) asked what distinct enforcement Decision Record's evidence requirements justified.

This guidance extends, without modifying, [CP-02 Architecture](../08_CAPABILITY_PACKS/CP-02_Product_Management_Intelligence_Pack/Architecture.md) §5–§6, the corresponding sections of [ARR.md](../08_CAPABILITY_PACKS/CP-02_Product_Management_Intelligence_Pack/ARR.md), and [ARCHITECTURE_FREEZE_v1.md](../ARCHITECTURE_FREEZE_v1.md)'s own memory-categorization precedent from CP-01. It is binding on every future pack via the [Version 1 Development Guide](../VERSION_1_DEVELOPMENT_GUIDE.md) §6 (Architecture Rules) and §16 (Technical Debt Policy) — a `memory_type` introduced without a genuine behavioral justification is the kind of unacceptable architectural debt that policy already rules out.

## Consequences

**Positive**: the `product_*` (and future `*_`) memory-type namespace grows only when a real behavioral distinction exists, keeping it small, meaningful, and easy for a new engineer to reason about in full. The precedent this ADR establishes is directly reusable by CP-03 onward without re-deriving it. CP-02's own Ownership Matrix (ARR §4) and ten-category catalogue (Architecture §6) remain unchanged and require no correction — this ADR formalizes a decision that was already implicit in them, rather than discovering a defect in them.

**Negative / accepted cost**: a reader of the Product Artifact Model (Architecture §7) who expects a strict one-to-one mapping between entities and memory types will find one exception (Portfolio) and must consult this ADR to understand why. This is judged an acceptable, well-documented cost — the alternative (a `memory_type` for every noun) is the larger, compounding cost this ADR exists to prevent.
