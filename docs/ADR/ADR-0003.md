# ADR-0003: Executive Agent Architecture

## Status

Accepted (implemented, M17 "Executive Agent (PID 1)").

## Context

By M17, the general Agent Framework (M16) existed — `BaseAgent`, `AgentContext`, `AgentRegistry`, `AgentExecutor` — but nothing yet occupied the role of "the agent that receives a request first and decides what happens." The platform needed a top-level coordinator: something that can break a request into steps, decide which steps a specialist should handle, and assemble a final response — informally, "PID 1" for the AI Operating System, borrowing the Unix convention for the first process a system starts.

## Problem

A top-level coordinator has different structural needs than a generic agent or a specialist:

- **Planning**: something has to turn "a user's request" into a structured, dependency-ordered set of steps.
- **Routing**: something has to decide which registered specialist (if any) should handle each step, without the coordinator needing to know about specialists by name.
- **Lifecycle**: unlike a one-shot specialist invocation, a top-level coordinator is expected to be ready for the next request immediately after finishing the current one — its state machine needs to reflect that.
- **Bounding delegation**: without an explicit policy, nothing stops a coordinator from delegating indefinitely deep, or invoking tools/web access a deployment doesn't want it to have.

## Alternatives Considered

1. **No dedicated planner/task-graph — the Executive calls specialists directly in whatever order its own code hardcodes.** Rejected: this couples the Executive's code to specific specialists and specific orderings, defeating the registry-based Open/Closed extension model the rest of the platform relies on.
2. **Route tasks by inspecting a `Decision` object's blanket boolean flags** (e.g. `Decision.requires_memory`) directly against specialist capabilities. Attempted first, then rejected after finding a real bug: matching on a blanket flag routes *every* task needing (say) memory access to a memory-capable specialist, even tasks whose actual work has nothing to do with memory retrieval.
3. **Route tasks by an explicit, task-scoped `required_capability` field** (`task.metadata["required_capability"]`), matched against what each specialist declared as `supported_tasks` at registration time. **Chosen**, after finding and fixing the problem with option 2.
4. **Reuse the generic `AgentState` machine as-is**, where `COMPLETED`/`FAILED` are terminal. Rejected: a coordinator that goes terminal after one request would need to be reconstructed for every subsequent request, which doesn't match how a long-lived coordinator is actually used.

## Decision

Build `ExecutiveAgent(BaseAgent)` with its own dedicated supporting types in `app/services/ai/agents/executive/`:

- `ExecutivePlanner(AgentPlanner)` — a deterministic, template-based planner producing a fixed 5-task plan shape (not adaptive; explicitly not attempting free-form planning in this milestone).
- `Task`/`TaskGraph`/`TaskResult` — `TaskGraph.execution_order()` returns a valid topological ordering via Kahn's algorithm, so a plan with inter-task dependencies executes in a correct order without a hardcoded sequence.
- `Dispatcher` — routes each `Task` via `task.metadata["required_capability"]` against `SpecialistRegistry`, never by inspecting `Decision`'s blanket flags directly.
- `Decision` — the planner's declared intent for a task, kept as a separate concept from the capability actually used for routing.
- `ExecutivePolicy` — `maximum_depth`, `maximum_retries`, `maximum_runtime_seconds`, `allow_web`, `allow_tools`, `allow_delegation`, `maximum_parallel_tasks` — a deliberately separate policy layer from `SpecialistExecutionPolicy` (which bounds one specialist) and Runtime's `RetryPolicy` (which bounds one provider call).
- `ExecutiveState`/`ExecutiveStateMachine` — `COMPLETED` and `FAILED` both loop back to `IDLE`, unlike the generic `AgentState` machine, reflecting that the Executive is meant to accept a new request immediately after finishing the previous one.
- `ExecutiveEvent`/`ExecutiveEventPublisher` — full lifecycle tracing (`PLAN_CREATED` through `RESPONSE_GENERATED`).

`ExecutiveAgent` self-registers in `AgentRegistry` under the name `"executive"` — it is a full `BaseAgent`, not a special-cased type, discoverable and constructible the same way as any other agent.

## Consequences

**Positive**: adding a new specialist never requires modifying `Dispatcher`, `ExecutivePlanner`, or `ExecutiveAgent` itself — registration alone (with accurate `supported_tasks`) is sufficient for the Executive to route to it. `TaskGraph`'s topological ordering means a plan's steps are never executed out of dependency order, even as plans grow more complex than the current 5-task template.

**Negative / accepted cost**: `ExecutivePlanner` is deterministic and template-based, not adaptive — the Executive currently "plans" by filling in a fixed template, not by reasoning about request complexity. This is an explicit, current limitation, not a hidden one (see [Executive_Agent.md](../05_AGENTS/Executive_Agent.md)). There is also no re-planning around a failed task today — a `TASK_FAILED` event is recorded and execution proceeds according to policy, but the Executive does not currently adjust its plan in response.

**A related gap surfaced by this decision**: `ExecutivePolicy.allow_tools` exists as a flag, but there is currently no path for the Executive to invoke a tool directly without going through a specialist — the flag is declared but not fully wired to an actual direct-tool-access capability. This is noted as a known gap in [Executive_Agent.md](../05_AGENTS/Executive_Agent.md) rather than silently left undocumented.
