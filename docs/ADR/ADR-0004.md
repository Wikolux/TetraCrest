# ADR-0004: Universal Tool Framework

## Status

Accepted (implemented, M17 "Universal Tool Framework").

## Context

Agents need reach beyond reasoning over text: search, computation, file access, business-system integrations. Without a shared framework, every agent that needs a capability like this would either call out to some ad hoc function directly, or (worse) each agent would grow its own bespoke notion of "a tool" with its own validation, permission, and error-handling conventions.

## Problem

A tool-invocation mechanism shared across every current and future agent needs to answer several questions consistently: how is a tool's expected input validated before it runs? How is permission to use a given tool enforced? How does a tool's execution get the same retry/timeout/cancellation/middleware/event treatment every other execution engine in the platform has? And critically — how does discovery work (which tools exist, what can they do) without needing to construct every registered tool just to ask?

## Alternatives Considered

1. **Let each agent call tool implementations directly, with its own error handling.** Rejected outright — this is exactly the "no shared execution infrastructure" problem the whole AI Operating System exists to avoid (see [Vision.md](../00_OVERVIEW/Vision.md)).
2. **Reuse `ConversationProvider`'s exact shape for tools** (treat a tool like a capability provider). Rejected: a provider answers "generate a response"; a tool answers "perform an action, possibly with side effects, requiring permission checks first." The permission/validation concerns are genuinely different enough to warrant their own contract rather than forcing tools into the provider shape.
3. **A dedicated `BaseTool` ABC with its own registry/factory/executor**, deliberately mirroring the Runtime's executor shape (retry/timeout/cancellation/middleware/events) for consistency, but adding validation and permission checks the Runtime has no equivalent of. **Chosen.**
4. **Derive tool discovery metadata (category/capabilities/permissions) by instantiating each registered tool class.** Rejected in favor of requiring this metadata at registration time — see Decision below.

## Decision

Build `app/services/ai/tools/`:

- `BaseTool(ABC)` — fully abstract execution contract, plus a **concrete** `manifest()` method building a `ToolManifest` from the tool's declared identity. Making `manifest()` concrete (rather than deferring it) was a deliberate scope decision made during the milestone itself, not part of the original plan — every tool needs a self-describing manifest for discovery, and there was no good reason to make every tool author re-derive that logic.
- `ToolRegistry(GenericProviderRegistry[str, ToolRegistration])` — `register()` requires `name`/`category`/`capabilities`/`permissions` as explicit keyword arguments at registration time, stored in a `ToolRegistration` record. This mirrors the same "registration-time metadata over instance introspection" pattern later reused for `SpecialistRegistry` — `category`/`capabilities`/`permissions` are abstract *instance* properties on `BaseTool` (each concrete tool decides its own), so a registry holding only classes cannot answer "what category is this" without constructing one; requiring the caller to state this once at registration means `ToolRegistry.categories()`/`.capabilities()` work directly off the registry, with no instantiation needed anywhere in discovery.
- `ToolExecutor` — validation (against the tool's `ToolSchema`) → permission check (`PermissionPolicy`) → middleware (`ToolMiddlewarePipeline`) → retry/timeout/cancellation (reusing `kernel.RetryPolicy` and `runtime.CancellationToken`/`RuntimeTimeout` directly, never re-implementing them) → events/hooks.
- `schema.py` (`ToolSchema`/`SchemaField`) — a pure-Python schema representation with no external validation library dependency, matching the platform's zero-unnecessary-dependency stance.
- `ToolContext` composing `SharedExecutionContext` plus holding a `CancellationToken`; `ToolResult` composing `ExecutionMetrics`.

## Consequences

**Positive**: adding a new tool never requires modifying `ToolExecutor`, `ToolFactory`, or `ToolManager` — registration with accurate metadata is sufficient for discovery, permission checks, and execution to all work correctly. Reusing `CancellationToken`/`RuntimeTimeout`/`RetryPolicy` directly (rather than re-implementing tool-specific versions) meant the Tool Framework's execution semantics are identical to the Runtime's from day one, with no separate learning curve.

**Negative / accepted cost**: as of M19, **no concrete tool has been built** — the framework is fully specified and tested (187 tests) using hand-written fakes, but has not yet been exercised by a real tool in production. This means the schema/permission/validation design, while internally consistent, has not yet been stress-tested against a real tool's actual needs (e.g. a tool with genuinely complex input validation, or one needing a permission model more nuanced than the current `PermissionPolicy` provides).

**A related gap surfaced downstream**: when the Specialist Framework (M18) was built on top of the Tool Framework, `SpecialistExecutionPolicy.retry_policy`/`timeout_seconds` were initially declared but never actually wired into the `ToolExecutor` a specialist constructs — a real gap, not anticipated by this ADR, closed by having `ResearchAgent` build a policy-configured executor explicitly. See [ADR](ADR-0003.md)-adjacent reasoning in [Specialist_Framework.md](../03_INTELLIGENCE/Specialist_Framework.md) — declaring a policy value object does not, by itself, guarantee it's consumed; each caller building an executor is responsible for actually applying it.
